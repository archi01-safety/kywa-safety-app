# KYWA Vercel 시험 계획과 검증 기록

2026-11-10 Render 대시보드에서 확인한 KYWA 운영 커밋은 939dbe4cdca9967766b6440610cd269100ee4f5b다. 같은 커밋에서 pilot/kywa-vercel을 분기했다. 앱의 세 메뉴가 이미 켜진 서버에서 얼마나 빨리 실제 데이터를 표시하는지 비교한다.

## 시험 구성

1. Render 시험 서버 kywa-safety-pilot-api는 Singapore의 무료 Docker 서비스다. 저장소 루트 kywa-next, 시험 브랜치, APP_ENV=development, AUTH_MODE=pin을 지정한다. 시험 시트·폴더·세션 키·PIN은 비공개 환경설정으로 주입한다. 기존 커밋에서 기준을 측정한 뒤 같은 서버에서 PILOT_READS=true로 개선 커밋을 측정한다.
2. Vercel 프로젝트 kywa-safety-pilot은 같은 브랜치와 루트 kywa-next를 사용한다. 프로덕션 추적 브랜치를 pilot/kywa-vercel로 지정한다. 정적 화면과 GET /api/overview, GET /api/assessments를 처리한다. 관리자 목록은 매 요청 Render 시험 서버의 PIN 세션 만료·철회 상태를 확인한다. 쓰기·인증·파일 요청은 동일 출처 외부 rewrite로 Docker 백엔드에 전달한다.
3. 시트 A:S, 숨김 관리 탭, 조치이력을 갖춘 시험 파일과 별도 비공개 Drive 폴더를 생성했다. 합성 평가 150건, 8개 시설, 12개 분류, 조치 완료 50건이다. scripts/seed_pilot.py는 기존 시험 파일을 보존한다. 패키지에 API 키·세션 비밀·실제 평가 자료를 넣지 않는다.
4. Vercel의 서버 환경변수는 SPREADSHEET_ID와 GOOGLE_SERVICE_ACCOUNT_JSON이다. 조회는 읽기 전용 OAuth 범위를 사용하고 시험 파일 제목을 확인한다. 읽기 전용 범위는 자격 증명 자체의 기존 권한을 축소하지 않으므로 등록 대상은 시험 프로젝트로 제한한다.
5. 시험 프로젝트의 **Ignored Build Step → Only build production**을 사용한다. 여기서 Production은 운영 사이트가 아니라 시험 브랜치 `pilot/kywa-vercel`이다. 이 제한은 다른 브랜치에 시험용 설정 파일이 없어도 적용된다. 시험 소스의 `git.deploymentEnabled`는 슬래시가 포함된 다른 브랜치도 제외한다. [Vercel 브랜치 설정](https://vercel.com/docs/project-configuration/git-configuration)

## 변경과 기능 검증

- 정상 조회는 단일 Sheets 요청으로 현재 행·행 식별 메타데이터·관리 상태를 읽는다. 숨김 레코드에는 기준 스냅샷 등이 포함된다. 행 내용·식별·상태가 일치하지 않으면 Render의 기존 동기화 경로가 처리한다. 원래 평가 등급·확인 필요 행·수정 충돌 방지와 단일 작성자를 유지한다.
- 공개 통계의 CDN 캐시는 30초, 관리자 목록은 private, no-store다. 화면은 연도별 마지막 통계를 표시하고, 관리자 목록은 메모리에서 세션·권한·조회 조건별로 재사용한다. 쓰기 후 갱신하고, 로그인 해제 시 개인 목록을 지운다. 저장·보고서 생성 시점에는 원본을 재확인한다.
- 브라우저에서 해석 가능한 사진은 방향을 보정해 최대 1600px·300만 바이트 JPEG로 전송한다. HEIC/HEIF 디코딩을 지원하지 않는 기기에서는 기존 Render 업로드 경로로 보낸다. 최초/개선 사진, 얼굴 블러, 제출 재조회, 세 보고서, 권한 만료를 시험한다.

## 실제 배포 및 업무 검증 (2026-11-10, 한국 시간)

- [Vercel 시험 주소](https://kywa-safety-pilot.vercel.app/) · [Render 시험 주소](https://kywa-safety-pilot-api.onrender.com/). 시험 브랜치에서 기동한 `4a78aa0`으로 측정했다. 8개 기관 운영 서비스의 설정·배포·시트는 건드리지 않았다. Render에 기존 공통 연동 그룹을 연결했고 Vercel 두 변수는 시험 프로젝트의 Production Secret이다.
- 실제 Vercel 도메인에서 공개 통계 150건/시설 8곳/완료 50건/분류 12개, 비로그인 목록 401 및 private/no-store를 확인했다. 서버에 재조회한 전체 목록과 통계를 두 호스트에서 20회 대조했다. 매번 일치했다.
- 브라우저에서 만든 합성 JPEG 8,820,734바이트 → 전송 JPEG 1,360,813바이트. Chromium이 디코딩하지 못한 실제 HEIC 파일 11,833,370바이트 → 같은 크기로 외부 rewrite를 지나 Render에서 변환. 두 업로드는 모두 HTTP 200, 미리보기 긴 변 1,600px 이하. iPhone으로 촬영한 원본이나 실제 Safari에서 검증한 결과는 아니다.
- 합성 사진의 얼굴 확인·처리 → 분석 → 제출 → 중복 재시도 → 재조회 → 개선조치·재평가 → 세 보고서 다운로드를 같은 시험 세션에서 확인했다. 처리 사진과 Drive 재조회 바이트가 일치했다. 실제 XLSX 12,515바이트, PDF 143,350바이트, 편집용 HWPX 20,525바이트를 검사했다. 로그아웃 직후 목록은 401이었다. 시험 제출 행만 삭제하고 원래 집계를 확인했다.
- 시험 시트에 구형 Streamlit 형식 행을 직접 추가했을 때 새 그래프와 목록 확인까지 12.782초, 위험상황을 직접 바꾼 후 갱신 요청과 표시 데이터 확인까지 8.291초였다(각 1회, HTTP). 잘못된 숫자가 입력된 행은 확인 대상으로 분리됐고 시험 행 삭제가 반영됐다. 즉시 갱신 조건의 값이며 다른 사용자의 30초 캐시가 자동으로 소진되는 시간은 포함하지 않는다.
- 실기기 측정은 양쪽 시험 주소에서 `/?pilot_measure=1`로 열고 **시험 관리자** 로그인 후 '실기기 측정 시작'을 누른다. 같은 휴대폰·한국 네트워크에서 화면을 켜두고 측정한다. 결과는 그 화면에만 남으며 관리자 이름·PIN·측정값을 외부로 보내지 않는다. 일반 화면에는 측정 도구가 없다. 기준 운영 커밋에는 이 도구가 없으므로 동일한 자동 실기기 측정으로 간주하지 않는다.

## 실측 기록

같은 PC에서 같은 비공개 Google Sheets의 150건을 읽고 집계했다. 각 방식 1회 예열 후 순서를 교대해 20회 반복했다. 두 방식의 연도·시설·분류별 집계가 매회 일치했다. 아래 값은 HTTP 화면 지연이나 Vercel 배포 성능이 아니다.

| 로컬 백엔드의 실제 Sheets 조회 | 중앙값 | 95백분위 | 조회당 Sheets 요청 |
|---|---:|---:|---:|
| 기존 records + summarize | 2169.5ms | 3994ms | 6 |
| 개선 read_records + summarize | 368.5ms | 405ms | 1 |

재표시 측정은 로그인 후 같은 탭 사이를 20회 이동한 Chromium 결과다. 단위는 ms이고 각 셀은 **중앙값 / 95백분위**다. 모바일 열은 Pixel 7 화면 에뮬레이션이다. 실제 모바일 네트워크/기기는 미측정이다.

| 배포 환경 | PC 목록 | PC 그래프 | 모바일 에뮬레이션 목록 | 모바일 에뮬레이션 그래프 |
|---|---:|---:|---:|---:|
| Render 기존 운영 커밋 (시험 서버) | 105.1 / 138.7 | 7525.6 / 8517.8 | 101.7 / 118.8 | 7966.4 / 8000.0 |
| Render 개선판 | 60.9 / 75.0 | 66.9 / 68.1 | 68.7 / 91.1 | 66.4 / 67.5 |
| Vercel 개선판 | 91.5 / 134.7 | 100.4 / 117.2 | 105.9 / 152.3 | 117.5 / 150.3 |

[화면 재표시 240개 측정값(CSV)](artifacts/pilot-ui-samples.csv): 3개 구성 × 2개 화면 크기 × 2개 화면 지표 × 20회. 측정값만 담고 계정·평가·사진 데이터는 담지 않았다.

기존 PC의 목록이 일부 빠르게 표시된 이유는 이전 목록이 이미 화면 메모리에 남아 있었기 때문이다. 그래프는 같은 조건에서 매번 다시 읽었고, 20회 중 한 번은 28.75초가 걸렸다. 기존 PC는 준비 동작을 포함해 화면에서 집계 23회·목록 43회를 요청했다. 개선판 PC에서는 양쪽 모두 집계 5회·목록 17회였다. 이는 브라우저 HTTP 요청 수이며, 표 위의 Google Sheets API 요청 수와 다르다. 공유 Google 할당량을 보호하기 위해 기존 커밋 반복 시험은 기기를 순차 실행하고 각 회 사이 18초, 개선판은 6초 간격을 뒀다. 간격 차이에 따라 30초 캐시가 갱신되는 횟수가 달라질 수 있다.

데이터 자체를 매번 읽는 HTTP 비교: 동일 PC·동일 150건·호스트 순서 교대·예열 후 각 20회. 그래프는 `fresh=1`과 매번 다른 쿼리로 집계 캐시를 우회했고, 목록은 인증 후 실제 전체 응답을 읽었다. 화면 표시 시간과 다르다.

| 배포 환경 | 집계 응답 ms(중앙값 / p95) | 관리자 150건 응답 ms(중앙값 / p95) |
|---|---:|---:|
| Render 개선판 | 761 / 1180 | 1812 / 2205 |
| Vercel 개선판 | 605 / 669 | 1106 / 1374 |

브라우저에서 데이터를 처음 표시할 때는 페이지를 매회 새로 열고 공개 집계 캐시를 우회했다. 같은 PC와 브라우저, 이미 기동한 두 호스트를 번갈아 20회 측정했다. 목록은 메뉴 클릭부터 첫 평가가 보일 때까지, 그래프는 대시보드 영역이 생긴 뒤 차트가 표시될 때까지다. 서버의 절전 해제 시간은 포함하지 않는다.

| 첫 표시 (중앙값 / p95, ms) | 관리자 목록 | 하단 그래프 |
|---|---:|---:|
| Render 개선판 | 1935 / 2464 | 694.5 / 1072 |
| Vercel 개선판 | 1430 / 1949 | 649 / 1022 |

시험 시트에서 직접 바꾼 자료도 실제 관리자 화면으로 비교했다. 각 셀은 편집이 저장된 직후 **목록 새로고침 → 변경 결과 표시**에 걸린 초이며, 구성별 한 건의 독립 시험이다. 현장 입력에서 새로 제출하는 시간, 자동 갱신 간격, 반복 측정의 중앙값과는 다르다.

| 배포 환경 | 직접 추가 | 위험상황 직접 수정 | 직접 삭제 |
|---|---:|---:|---:|
| Render 기존 커밋 | 6.118 | 7.599 | 4.577 |
| Render 개선판 | 12.762 | 8.163 | 5.635 |
| Vercel 개선판 | 8.700 | 9.739 | 7.140 |

모두 정확한 새 내용·삭제를 표시했고 해당 시험 행만 정리해 매번 150건을 복구했다. 직접 변경된 행은 정합성 복구를 거치므로 일반 조회와 같은 속도 향상은 관찰되지 않았다. 이 경로는 향후 운영 적용 시 별도로 확인할 대상이다. 재현: `python scripts/check_pilot_edits.py <시험주소> --ui` (시험 인증정보 및 Playwright Chromium 필요).

**판단: 운영은 Render를 유지하고, 시트 조회와 화면 캐시 개선부터 선별 적용하는 것을 권장한다.** Vercel에서 첫 목록은 505ms(26.1%) 단축됐지만 첫 그래프 차이는 45.5ms(6.6%)였다. 다시 본 화면의 p95는 PC 기준 Vercel 목록 135ms·그래프 117ms로, Render의 75ms·68ms보다 10% 이상 길었다. 절대 차이는 작지만 사전에 정한 이전 조건을 모두 만족하지 않았다. 두 개선판 모두 반복 표시 중앙값 0.5초 목표를 통과했다.

채택을 결정하더라도 운영 Render의 `PILOT_READS`를 켜거나 시험 시트 ID를 운영에 복사하지 않는다. 현재 고속 조회 코드는 시험 파일과 개발 모드에서만 실행하도록 제한했다. 운영용으로는 KYWA의 기존 권한·행 식별 검사를 보존하면서 단일 조회와 화면 재표시 개선만 옮기고 운영 사본에서 직접 수정·삭제 및 여러 역할의 조회를 대조해야 한다. 이번 시험은 데이터 이관이나 호스팅 전환을 수행하지 않는다.

재현하려면 시험 관리자 PIN을 로컬 환경변수 `PILOT_PIN`에만 설정한다. `frontend/scripts/bench-pilot.mjs <시험주소> desktop`은 탭 재표시, 같은 명령의 `mobile-emulation`은 Pixel 7 화면 모사, `frontend/scripts/bench-first.mjs`는 새 페이지 첫 표시를 측정한다. 호스트는 시험 주소로 제한했다. 두 호스트를 한 번에 오래된 코드로 조회하면 Google Sheets 할당량 때문에 비교가 왜곡될 수 있어 기존 버전 측정은 순차 수행한다.

같은 한국 네트워크에서 서버를 깨운 뒤 메뉴 클릭부터 실제 목록 표시까지, 입력 화면 표시부터 그래프 표시까지를 비교한다. 첫 조회와 반복 조회를 구분한다. 각 기기·환경에서 20회 측정하고 중앙값과 95백분위를 기록한다. 직접 시트 수정과 삭제는 시험 자료만 사용한다. 목표는 기존 화면 재표시 중앙값 0.5초 이내다. 기능 통과 후 Vercel이 개선 Render보다 주요 지표 하나 이상에서 20% 및 0.3초 이상 개선되고 나머지 주요 지표의 95백분위가 10% 이상 악화되지 않을 때 이전 후보로 검토한다. 시험 종료 시 시험 서비스·도메인만 중지할 수 있다.
